# GPS 보조 감지 + 도보 경로 안내 (실험 작업 공간)

작성일: 2026-10-15 · 기반: `minjae-main` 웹앱 (YOLO 객체 감지 + 진동 알림)

이 폴더는 아래 기능을 실험하는 별도 작업 공간이다. 결과가 쓸 만하면 본 저장소로 옮기고, 아니면 폐기한다.

## 1. 무엇이 가능하고 무엇이 안 되는가

| 요청 | 웹에서 가능? | 구현 상태 |
|---|---|---|
| GPS로 횡단보도가 진행 방향 앞에 있으면 모델 정확도가 낮아도 진동 | 가능 | 구현됨 (`detectWithGps`) |
| 도착지 입력 → 가장 효율적인 도보 경로 탐색 | 가능 (OSRM foot, 키 불필요) | 구현됨 |
| 최단 경로뿐 아니라 인파 밀집도 고려 | 가능 | 구현됨 (`crowd.js`). 전국: 지도 지점 종류별 가중 밀도 × 시간대. 서울: 서울시 실시간 도시데이터 121곳 혼잡도 (키·중계 서버 필요, 4절) |
| 경로 이탈 시 실시간 재탐색 | 가능 | 구현됨 (30m 이상 벗어남이 3회 연속이면 재탐색) |
| GPS/지도에서 기둥·횡단보도 자료를 얻어 모델 보완 | 가능 | 구현됨 (OpenStreetMap Overpass). 단, 한국은 가로등·전봇대 데이터가 거의 없음 |
| 설정에서 on/off, 도보 한정 | 가능 | 구현됨 |
| **백그라운드 상태에서도 경로 안내** | **웹에서는 불가** | 대신 화면 꺼짐 방지(Wake Lock) + 음성 안내로 화면을 안 봐도 되게 함 |
| 추가 AI 모델 | **불필요** | 경로·인파·위험물은 모두 지도 데이터로 처리. 인파 예측 모델은 선택 사항 (4절) |

웹 브라우저는 탭이 백그라운드로 가면 카메라·위치 갱신·진동·타이머를 멈추거나 크게 늦춘다. iOS Safari는 더 엄격하다.
백그라운드 안내가 꼭 필요하면 PWA가 아니라 네이티브 앱(Android 포그라운드 서비스)으로 가야 한다.

## 2. 구조

```
index.html   화면 (길찾기 패널, 지도, 설정 토글 추가)
main.js      기존 감지 루프 + detectWithGps() + 길찾기 UI
geo.js       위치·나침반·Overpass 위험물·진행 방향 앞 위험물 계산
route.js     주소 검색·도보 경로·점수화·안내·이탈 재탐색·음성
crowd.js     인파 추정: OSM 지점 가중치 × 시간대 (전국) + 서울 실시간 혼잡도 (선택)
seoul_areas.json          서울 도시데이터 121개 장소의 위경도 (tools/geocode_seoul_areas.py 로 생성)
netlify/functions/seoul.js 서울시 API 중계 (배포용). tools/dev_proxy.py 는 같은 역할의 PC 테스트용
samples/mock 오프라인 테스트용 실제 API 응답 (서울시청 → 서울역) + seoul_ppltn.json(가짜 혼잡도)
```

### 데이터 소스 (모두 무료, 키 없음)

| 용도 | 서비스 | 비고 |
|---|---|---|
| 주소 검색 | Nominatim (OpenStreetMap) | 초당 1회 제한. 상업 배포 시 자체 호스팅 권장 |
| 도보 경로 | OSRM foot 프로파일 (routing.openstreetmap.de, FOSSGIS) | 대안 경로 3개, 한국어 도로명 포함. 경량 사용만 허용 |
| 위험물·POI | Overpass API (overpass-api.de 외 미러 2곳) | **공개 서버가 자주 502/504**. 미러 3곳 순차 시도 + 위치별 캐시. 실제 서비스는 자체 Overpass 또는 사전 추출 데이터 필요 |
| 지도 타일 | tile.openstreetmap.org | 출처 표기 필수 |
| 서울 실시간 인파 (선택) | 서울 열린데이터광장 실시간 도시데이터 `citydata_ppltn` | 무료지만 **인증키 필요**, HTTP 전용·CORS 없음 → 중계 서버 필수. 샘플 키는 광화문·덕수궁만 |

## 3. 동작 원리

### 3-1. GPS 보조 감지 (`main.js: detectWithGps`)

1. `Geo.hazardsAhead()` 가 현재 위치에서 35m 안, 진행 방향 ±45° 안의 지도상 위험물을 돌려준다 (6m 안이면 방향 무관).
2. 그 종류(횡단보도·계단·기둥)에 한해 모델 신뢰도 임계치를 **0.25 → 0.10** 으로 낮춘다. 즉 "앞에 횡단보도가 있을 것"이라는 지도 정보가 있으면 모델이 희미하게만 봐도 감지로 인정한다. 목록에 `+GPS` 로 표시.
3. 모델이 전혀 못 봤는데 위험물이 아주 가까우면(횡단보도 15m, 계단 10m, 기둥 6m) **가상 박스**를 만들어 경고한다. 박스의 좌우 위치는 상대 방위(왼쪽/정면/오른쪽), 높이는 거리에 비례. 점선 박스와 `GPS 8m` 표시로 구분.
4. 이후는 기존 흐름과 같다: 위험도 계산 → 3프레임 확정 → 방향별 진동 + 화면 깜빡임.

진행 방향은 걷는 중에는 GPS 이동 방향, 멈춰 있으면 나침반(DeviceOrientation)을 쓴다. iOS는 나침반 권한 창이 뜬다.

### 3-2. 경로 탐색과 점수 (`route.js: plan / score`)

1. OSRM 에서 대안 경로를 최대 3개 받는다.
2. 경로 전체를 덮는 사각 영역의 위험물과 POI(상점·음식점·역·정류장 등)를 Overpass 에서 한 번에 받는다 (영역이 6km 이상이면 생략).
3. 경로마다 점수 = 소요 시간(초) + 가산:

| 항목 | 가산 (초) | 의미 |
|---|---|---|
| 횡단보도 1곳 (경로 15m 이내) | +25 | 신호 대기·차량 위험 |
| 계단 1곳 (12m 이내) | +40 | 낙상 위험, 이동약자 불리 |
| 기둥 1곳 (6m 이내) | +2 | 충돌 위험 (데이터 적음) |
| 인파 지수 1 (아래 3-4) | +0.8 × 강도 | 사람 많은 길 회피 |
| 서울 실시간 "약간 붐빔" 장소 300m 이내 통과 | +60 × 강도 | 실제 측정 혼잡도 |
| 서울 실시간 "붐빔" 장소 300m 이내 통과 | +150 × 강도 | 실제 측정 혼잡도 |

4. 점수가 가장 낮은 경로를 선택한다. 가산값은 `route.js` 의 `PENALTY`, 인파 쪽은 `crowd.js` 의 `STRENGTH`·`LEVEL_PENALTY` 에서 조절한다. 강도(설정 "인파 회피")는 끔 0 / 약 0.5 / 중 1 / 강 2.

### 3-4. 인파 밀집도 추정 (`crowd.js`)

두 겹으로 되어 있고, 설정에서 끔/약/중/강을 고른다.

**① 전국 공통 (키 없음)** — OpenStreetMap 에서 사람이 모이는 지점을 받아 종류별 가중치로 더한다.

| 지점 종류 | 가중치 | 지점 종류 | 가중치 |
|---|---|---|---|
| 철도역·지하철 출입구 | 3.0 | 음식점·카페·영화관 | 1.0 |
| 시장·백화점·마트·쇼핑몰 | 2.5 | 일반 상점 | 0.8 |
| 학교·대학 | 2.0 | 공원·관광지 | 0.8 |
| 버스 정류장·터미널 | 1.2 | 그 외 | 0.5 |

경로 35m 안의 가중치 합 ÷ 경로 길이(km) × 시간대 계수 = **인파 지수(/km)**.
시간대 계수: 평일 출근 7:30~9:30 ×1.6, 점심 11:30~13:30 ×1.3, 하교 15:00~16:30 ×1.2, 퇴근 17:30~19:30 ×1.6, 심야 22~06시 ×0.5, 주말 오후 13~19시 ×1.4, 나머지 ×1.0.
한계: "그 시각에 실제로 몇 명 있는가"가 아니라 "사람이 모일 만한 곳이 얼마나 많은가"다. 전국 어디서나 동작한다는 것이 장점.

**② 서울 실시간 (선택, 설정에서 켬)** — 서울시가 121개 장소의 실시간 인구와 혼잡도(여유/보통/약간 붐빔/붐빔)를 5분 단위로 낸다.
- 브라우저에서 직접 부를 수 없어(HTTP 전용, CORS 없음) 중계가 필요하다: Netlify 배포는 `netlify/functions/seoul.js` 가 자동으로 붙고(`/.netlify/functions/seoul`), PC 는 `py -3 tools/dev_proxy.py` (포트 8002).
- 인증키는 서울열린데이터광장에서 발급받아 설정에 입력한다 (localStorage 에만 저장, 코드에 넣지 않음). Netlify 환경변수 `SEOUL_API_KEY` 로 서버에 둘 수도 있다. 비우면 샘플 키가 쓰이는데 광화문·덕수궁만 응답한다.
- 경로 좌표에서 300m 안에 있는 장소만(최대 8곳) 조회하고 5분 캐시한다. 결과는 지도에 색 원(초록→빨강)으로 표시.
- 장소 좌표(`seoul_areas.json`)는 Nominatim 으로 지오코딩했고 실패한 6곳은 수동 입력. 정확도는 장소 중심 기준 수십~수백 m.

### 3-3. 안내와 이탈 재탐색 (`route.js: update`)

- 현재 위치를 경로 선분에 투영해 남은 거리와 경로 이탈 거리를 구한다.
- 각 안내 지점(회전)은 경로 좌표열의 몇 번째 점인지 기록해 두고, 진행 위치가 그 점을 지나면 통과 처리한다. GPS 가 띄엄띄엄 들어와도 지점을 건너뛰지 않는다.
- 다음 지점 25m 안에서 한 번 음성 안내 ("20m 앞에서 왼쪽으로 가세요 (무교로)").
- 경로에서 30m 이상 벗어난 위치가 3회 연속이면 현재 위치에서 재탐색하고 "경로를 벗어났습니다" 안내.
- 목적지 15m 안이면 도착 처리.

## 4. 인파 밀집도를 더 넓히려면

- **서울 밖 실시간 데이터**: 전국 단위의 공개 실시간 유동인구 API 는 없다. 지자체별로 비슷한 것이 생기면 `crowd.js` 의 서울 계층과 같은 방식(장소 표 + 중계)으로 추가한다. 통신사 유동인구(SKT·KT)는 유료.
- **자체 예측 모델 (선택)**: 서울 API 를 1~2주간 10분 간격으로 저장(장소, 요일, 시각, 날씨 → 혼잡도)한 뒤 간단한 분류 모델(scikit-learn GradientBoosting)로 "이 시각에 이 장소가 붐빌 확률"을 예측한다. 결과는 JSON 표(장소×요일×시각)로 내보내 웹에서 조회만 하면 되므로 브라우저에서 모델을 돌릴 필요가 없다. 지금의 시간대 계수를 이 표로 바꾸면 된다.
- **서울 실시간을 켜려면**: 서울열린데이터광장(data.seoul.go.kr) 가입 → 인증키 발급 → 설정 ▸ 인파 회피 ▸ "서울 실시간 혼잡도 사용" 켬 → 인증키 입력 → "연결 확인". Netlify 에 올릴 때는 저장소에 `netlify/functions/` 가 있으면 함수가 자동 배포된다.

## 5. 테스트 방법

- 실기기(HTTPS 필요): 시작하기 → 위치 권한 허용 → 길찾기 패널에서 도착지 검색 → 안내 시작.
- PC 오프라인 테스트: `index.html?mock=1&image=samples/street2.jpg&lat=37.5665&lon=126.9780&heading=200`
  - `mock=1` 은 저장된 API 응답을 쓴다 (서울시청 → 서울역). 네트워크 없이 동작.
  - 🚶 시뮬레이션 버튼: 경로를 따라 자동 이동하며 음성 안내·도착을 확인.
  - 콘솔에서 `Geo.simulate(lat, lon, heading)` 으로 위치를 임의로 옮겨 이탈 재탐색을 확인.
- 검증된 것 (2026-10-15, 오프라인 모드): 지도상 8m 앞 횡단보도 → GPS 가상 박스 경고, 대안 경로 2개 점수화·선택, 회전 음성 안내 3회, 이탈 재탐색.
- 검증된 것 (2026-10-16, 오프라인 모드): 인파 지수 68/km vs 63/km 로 대안 비교, 서울 실시간(가짜 응답) 6곳 적용·지도 표시, 설정의 "연결 확인" 동작. 중계 서버 `tools/dev_proxy.py` 는 샘플 키로 광화문·덕수궁 실제 응답 확인(curl).
- 서울 실시간 PC 테스트: 터미널에서 `py -3 tools/dev_proxy.py` 를 켜 두고 `mock=1` 없이 접속해야 실제 API 가 호출된다 (OSRM·Overpass 도 실제 서버 필요).

## 6. 남은 과제

- Overpass 공개 서버 불안정 → 자주 가는 지역의 위험물 데이터를 미리 받아 파일로 넣는 방식(현재 mock 구조 재사용) 또는 자체 서버.
- 한국 OSM 에는 가로등·전봇대가 거의 없어 기둥은 여전히 카메라 모델에 의존.
- 백그라운드 안내는 네이티브 앱 과제.
- 음성 안내와 위험 진동이 겹칠 때의 우선순위 (현재는 둘 다 울림).
- 인파 가중치·시간대 계수는 상식 기반 추정값. 서울 API 를 모아 보정하면 좋다.
- 서울 장소 좌표는 지오코딩 결과라 일부는 중심이 치우칠 수 있다 (예: 관광특구처럼 넓은 곳).
